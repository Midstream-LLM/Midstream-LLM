# DeepSeek-V3 风格 MTP：3060 单卡单变量试验（2026-11-25）

## 分支

MTP 只在 **`feat/mtp-3060`** 分支上。它基于 `feat/doc-attention-8xv100`，所以代码里也包含文档隔断、Muon、DDP，但本配置都没有开启。8×V100 的分支已经 revert 了 MTP，不会把 MTP 带进那边的训练。

## 目的

只开 MTP（multi-token prediction，一次预测多个后续 token），其余设置都与 3060 上的 2K blocks 基线（`configs/jishui-200m-corpus-date-open-v3-blocks.json`）相同：因果注意力，不加文档隔断；优化器用 AdamW，不用 Muon；单卡；2K 窗口；学习率 1e-4 → 1e-5；同一份数据。这样可以单独看出 MTP 对主模型的影响。8×V100 那一路（文档隔断 + Muon + DDP）**不开 MTP**。

## 结构（`src/jishui/model_torch.py`）

`ModelConfig.mtp_depth = D`，默认 0。为 0 时 `to_dict` 不输出这个字段，所以旧 checkpoint 和 SFT/推理的配置都不受影响。

第 k 个 MTP 模块的计算如下（k = 1..D，按顺序串联）：

```
h_k[i] = Block_k( W_k · [Norm(h_{k-1}[i]) ; Norm(Emb(t[i+k]))] )
logits_k[i] = Head(Norm_k(h_k[i]))     → 预测 t[i+k+1]
```

- `h_0` 是主模型最后一层的输出（final norm 之前），与 DeepSeek-V3 相同。
- `Emb` 和 `Head` 与主模型共用（本模型的 tied embedding）。每个模块各有两个输入 norm、一个 2d→d 的投影 `W_k`、一个完整的 Transformer 块和一个输出 norm。D=1 时新增约 690 万参数，参数名都在 `mtp.*` 下。
- 位置 i 只用到 `t[≤i+k]`，满足因果性，有测试覆盖。
- `forward(input_ids)` 不传 `mtp_inputs` 时只返回主 logits，所以推理和 SFT 不会经过 MTP。

## 目标函数（`mtp_lm_loss` + trainer）

```
L = L_main + λ · mean_k L_mtp_k，λ = 0.3（DeepSeek-V3 前期的取值），D = 1
```

- 主 loss 和每个深度的 MTP loss 都按**整个 update 的全局有效 token 数**加权，所以结果不依赖梯度累积或 DDP 如何切分数据，有测试覆盖。
- 数据来自 `block_data` 预留的 lookahead（`prediction_offsets: [1, 2]`）。偏移大于 1 的目标如果和输入位置不在同一篇文档，会被屏蔽：EOD 归属它结束的那一篇，所以每个文档边界处会少训 1 个 MTP 目标。
- 日志里的 `train/loss` 仍是纯下一 token 的 loss，可以和基线直接比较。另外单独记录 `train/mtp_loss` 和 `train/mtp1_loss`。
- **验证只评主头的下一 token loss，并且固定使用 NTP 的 block 协议。** 因此协议指纹应与 2K blocks 基线相同（seed 20261118，128 块，259,906 tokens），可以直接和基线最终的 3.237 比较。启动日志里会打印 protocol 指纹，请核对。

## checkpoint

- 严格 resume 要求模型配置完全一致，包括 `mtp_depth`。
- `--init-from` 只加载权重时允许两个方向：
  - MTP 的 checkpoint 加载到普通模型：丢掉 `mtp.*`。
  - 普通 checkpoint 加载到 MTP 模型：MTP 模块从随机初始化开始。
- 导出给 SFT/推理时用 `checkpoints_torch.strip_mtp(state_dict, model_config)` 去掉 `mtp.*` 和 `mtp_depth`，得到的主模型与原架构完全相同（有测试覆盖）。

## 配置 `configs/jishui-200m-v3-mtp1-3060.json`

由基线配置复制而来，只改了以下几处：

- `model.mtp_depth: 1`
- `pretraining.prediction_offsets: [1, 2]`
- `pretraining.mtp: {"depth": 1, "weight": 0.3}`
- `target_tokens: 4,000,006,144`，与基线的累计预算相同，从零开始训练。
- tracking 名称改为 `jishui-200m-v3-mtp1-3060`。

计算量预计比基线多 10–15%（一个额外的 Transformer 块和一次输出层计算），显存多出约一份 2K×32768 的 logits。基线峰值为 6.31 GiB，12 GB 的 3060 放得下。

## 3060 上的操作

```bash
git fetch origin && git checkout feat/mtp-3060 && git pull   # 独立分支，不要用 8×V100 的分支
CUDA_VISIBLE_DEVICES= PYTHONPATH=src .venv-torch/bin/python -m unittest \
  tests.test_mtp tests.test_corpus_pretraining tests.test_block_data tests.test_torch_continuation
bash scripts/train_3060_mtp.sh smoke
bash scripts/train_3060_mtp.sh start
bash scripts/train_3060_mtp.sh resume   # 中断后严格恢复
```

- 启动前先确认 3060 是空闲的（`nvidia-smi`），不要停掉或改动其他正在运行的 run。
- smoke 阶段要核对：
  - 日志中出现 `mtp_depth=1`；
  - `mtp_loss` 有限，并且高于主 loss（预测第 2 个 token 更难）；
  - tok/s 约为基线的 85–90%；
  - `peak_vram_gib` 在 12 GB 以内；
  - 验证协议指纹与基线一致。

## 怎么判断有没有用

- 主要指标：同 token 数下的固定验证 loss，和基线逐点比较（基线日志在 `runs/jishui-200m-corpus-date-open-v3-blocks`）。
- 其次：用 `strip_mtp` 导出后，按同一套 SFT 配方训练，再用 `runs/evaluations/20261125-3060-sft-2k` 的评测脚本比较。
- 参考：DeepSeek-V3 报告 MTP 在大模型上有收益；对 200M 这么小的模型是否有效没有定论，所以先做这一个变量的对照。

## 测试（`tests/test_mtp.py`，11 项，跳过 1 项）

- 配置往返；`mtp_depth=0` 时不输出该字段。
- 主 logits 不受 MTP 影响；MTP 满足因果性。
- 未来 token 的输入和目标对齐正确，且不跨文档。
- MTP loss 的梯度能传回主模型和 embedding；某个深度没有有效目标时安全返回 0。
- `strip_mtp` 导出的主模型与原模型逐位一致。
- 2 进程 DDP 与单进程结果一致。
- 中途恢复后逐位相同；验证协议指纹与非 MTP run 相同；`--init-from` 两个方向都能加载；配置不一致时报错。

全部测试合计 78 项通过（跳过 2 项），均在本地 CPU 上运行，**尚未在 3060 上实测**。
