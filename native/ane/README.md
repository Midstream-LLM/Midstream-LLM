# Jishui on Apple Neural Engine

This directory is a vendored, Jishui-specific adaptation of the dynamic
training path from [maderix/ANE](https://github.com/maderix/ANE), pinned while
this integration was developed at commit `d91c9845c0784dec7753048954fc6d0e8411fe29`.
The upstream source is MIT-licensed; see [ANE-LICENSE](ANE-LICENSE).

The implementation uses Apple's private `_ANE*` APIs through Objective-C
runtime lookup. It is a research path, not a supported Apple API. It must run
outside a restricted/sandboxed process because the ANE compiler talks to
system services. macOS 15+ on Apple Silicon is required.

> **Host safety:** do not run kernels or test binaries copied directly from
> `imperatormk/ane-train` on this macOS 15.7.1 M4 host. Its macOS-26-oriented
> `modules/test_bwd` hit a null-IOSurface `SIGSEGV` and a system-level
> `SOCD report detected: (iBoot async abort)` / `AMCC error` panic on
> 2026-08-09. Static mapping puts the user-space write at `test_bwd.m:163`,
> but the preceding ANE/AMCC illegal-DMA records indicate that the
> macOS-26-oriented backward/Adam program likely invalidated the mapping first;
> the ignored lock/base check was a secondary fault. Issue #47 is source-level
> evidence only here. New interop work must pass a Metal-only test before it
> touches this checked-in ANE path.

## What is implemented

- Jishui-200M dimensions: `D=704`, `L=30`, `H=KV_H=11`, `HD=64`,
  `FFN=1856`, `vocab=32768`.
- Jishui LayerNorm (affine gamma + beta), standard residuals, SwiGLU, tied
  embedding/language head, and MLX-compatible split-half RoPE.
- Dynamic ANE MIL kernels for the matrix-heavy forward/backward `dx` path.
- Optional custom Metal kernels for LayerNorm forward/backward and fused SiLU
  backward (`--metal-norm --metal-silu`). Full-vocabulary cross entropy uses
  token-major `[SEQ,VOCAB]` storage; bounded asynchronous dW accumulation and
  AdamW remain on CPU/Accelerate. This is heterogeneous
  ANE+GPU+CPU operator placement, not a pure-NPU trainer or model-replica DDP.
- The kernels retain GQA tiling/reduction support because the implementation
  is shared with Qwen-style models. Jishui-200M itself uses `KV_HEADS=HEADS`
  (ordinary MHA), so there is no GQA memory/throughput claim for this model.
- The checked-in Qwen3 GQA header is reference-only: its 151,936-token
  vocabulary cannot be represented by the current uint16 NPY/index format and
  is rejected at compile time rather than running with truncated IDs.
- A versioned fp32 checkpoint with dimension checks and resume support.

## Build

From the repository root:

```bash
cd native/ane/training_dynamic
make MODEL=jishui_200m_2048
```

`jishui_200m` uses `SEQ=256` for a practical first benchmark. The production
context graph is `MODEL=jishui_200m_2048`. Metal submission overhead makes the
optional GPU path slower at seq 256; use it only with the production graph.

## Data

The frozen Jishui shards are NPY containers. For a bounded, reproducible
benchmark slice, export fixed records with:

```bash
PYTHONPATH=src .venv/bin/python scripts/export_ane_batches.py \
  --data-dir dataset/processed \
  --output /private/tmp/jishui_ane_records.u16 \
  --records 128 --seq-len 256
```

Each record is `seq_len + 1` little-endian `uint16` ids. It is generated by
the same train-only, category-balanced `PackedBatchIterator` used by MLX and
contains EOD (`id=2`) at document boundaries. Run it with:

```bash
cd native/ane/training_dynamic
make MODEL=jishui_200m
./train --scratch --records --data /private/tmp/jishui_ane_records.u16 \
  --steps 10 --accum 1 --log-interval 1 --no-checkpoint
```

This bounded record file uses `SEQ=256`, so it intentionally runs the CPU/ANE
baseline. The optional Metal kernels are measured and recommended only with
the production `jishui_200m_2048` graph below.

The exporter intentionally requires an explicit record count; it will not
silently materialize the multi-billion-token corpus. For a real train run,
export only the small document index and let the native loader mmap the frozen
shards on demand:

```bash
PYTHONPATH=src .venv/bin/python scripts/export_ane_index.py \
  --data-dir dataset/processed \
  --output /private/tmp/jishui_ane_train.index

cd native/ane/training_dynamic
make MODEL=jishui_200m_2048
./train --scratch \
  --index /private/tmp/jishui_ane_train.index \
  --data-dir /Volumes/PS2000/LLM/Jishui/dataset/processed \
  --optimizer-steps 100 --accum 10 \
  --metal-norm --metal-silu
```

Index mode is train-only, token-weighted within the selected category, and
inserts EOD id 2 at document boundaries. Index format v2 stores the sampling
mixture and EOD id; v1 indexes remain readable for compatibility. The data
directory is explicit because relative paths are resolved against the process
working directory.

The loader maps the original shard files in place. Keep the ExFAT volume
mounted and awake for an overnight run; if macOS drops the volume while a
mapping is active, the process can receive `SIGBUS`. Copying the shards to an
internal APFS volume avoids that hardware/storage failure mode at the cost of
roughly 8 GB of additional local space.

## Checkpoint and monitoring

`--checkpoint PATH` selects a checkpoint prefix. `--save-interval N` saves
every N completed optimizer updates and a final point is written at the end.
`--save-interval 0`
disables periodic saves but still writes that final point; use
`--no-checkpoint` for disposable benchmarks that must not write any checkpoint.
For Jishui-200M each native fp32 model+Adam checkpoint is about 2.4 GB, so this
flag matters for one-step gates. Checkpoints are written atomically as
`PATH.step_XXXXXXXX`; the default
`--keep-checkpoints 3` prunes older files. `--resume` accepts either an exact
file or the prefix and selects the newest version automatically. Checkpoint v6
restores model/Adam state plus accumulation, warmup, LR, Adam, clipping and loss
scale settings; old v5 experimental files are rejected because they predate the
residual-consistency fix. `--optimizer-steps N` expresses a budget in optimizer
updates; with `--accum K` it runs `N*K` microsteps. `--warmup N` is also measured
in optimizer updates. A final partial accumulation group divides by its actual
microstep count. Logs include loss, timings, gradients, optimizer LR and a
sample weight delta. `--parity-report FILE` writes JSONL probes for comparing
CPU and Metal runs without saving a multi-gigabyte checkpoint.

## Current measured gate

The corrected standard-residual graph produced finite loss and nonzero updates
at both `SEQ=256` and `SEQ=2048`. The production-length `--metal-shadow` gate
checked every LayerNorm and SiLU invocation against its CPU reference and
completed one real-shard Adam update. Metal reductions are numerically close,
not bitwise identical: the first index-sampled loss was `10.4381037` on CPU and
`10.4381294` on Metal. A bounded-record gate retained loss `10.4834` and the
same sampled weight update across the paired backends.

After changing classifier logits to token-major order and bounding the async dW
queue, a cool-state paired run measured **5.6265 s** for ANE+CPU and **4.0101 s**
for ANE+Metal, a **1.40x** end-to-end improvement. The Metal timing breakdown
was 0.670 s ANE forward, 1.663 s ANE backward, 0.488 s total LayerNorm, 0.059 s
SiLU, 0.218 s classifier/loss/backward, and no exposed CPU dW wait. Absolute
times still vary with temperature and other GPU users. Standalone
`MPSMatrixMultiplication` remains slower than Accelerate for classifier and dW,
and `cblas_wait=0` shows that the current asynchronous CPU dW is already hidden.

A separate same-seed, three-update real-index gate measured 5.555 s/step on
ANE+CPU and 4.680 s/step on ANE+Metal (15.8% faster). Its CPU losses were
`10.4381 / 10.4182 / 10.0967`; Metal reported
`10.4381 / 10.4201 / 10.1042`, with a third-update relative loss difference of
`7.4e-4` and a maximum absolute difference of `1.41e-5` across the sampled
weights. Under the earlier live-MLX and heavy-swap load, the same production
shape was effectively tied at 20.654 s versus 20.467 s. These are short gates,
not a sustained-throughput claim.

Replicating the whole model independently on ANE and GPU is not recommended on
this 24 GB unified-memory, fanless host: it would duplicate parameters,
activations and optimizer state, require a custom gradient reduction path, and
make two asymmetric workers compete for memory bandwidth and thermal budget.
The supported experiment is the operator-level placement above.

The private API may break after a macOS update. Do not use this path for the
V100 cluster; that path remains PyTorch fp16/DDP as specified in `AGENTS.md`.
